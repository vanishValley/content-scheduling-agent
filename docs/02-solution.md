# 实现与文件说明

## 一次请求如何执行

CLI 读取请求与合成环境，校验字段，然后进入有上限的循环。每轮模型看到原始请求和已执行工具的结果，选择一个动作。程序校验动作参数、执行工具，再把结果交给下一轮模型。模型选择 `finish` 或达到上限后结束。

```text
请求校验 → 模型选择工具 → 参数校验 → 执行工具
                ↑                    │
                └──── 工具结果 ──────┘
                │
                └→ finish → 按实际记录汇总状态
```

真实模式中，工具调用来自模型服务返回的 `tool_calls`。`LiveProvider` 不按结果替模型挑选下一步。确定规则负责限制写入权限，例如“未审核不能保存”；它们不代替模型决定“补查还是结束”。

离线模式中的条件策略位于单独的 `MockProvider`，用途与边界在 README 和每份运行记录的 `provider.kind` 中标明。

## 动态决策发生在哪里

正常素材可以走“读取、规则检查、查询、保存、结束”。M04 首次检查缺少版权字段，但工具说明有补充资料，下一步应再次读取并复查。M02 没有补充资料，继续读不会产生新证据，应结束并请求补充。

查询返回 18:00 占用、19:00 空闲时，模型选择 19:00 保存建议。把占用改为 19:00、保留 18:00 空闲后，同一个 18:00 请求应回到原时段。区别来自本次工具观察，不是提前写进 Trace 的决策故事。

保存返回失败时，模型可以结束，也可以在步数范围内补救；最终状态只能依据保存工具的实际结果。成功读取的资料仍在上下文中，不会被失败覆盖。

## 工具职责

| 工具 | 输入 | 返回和限制 |
| --- | --- | --- |
| `read_material` | 素材 ID | 元数据、是否存在补充资料；仅允许请求内的 ID |
| `check_rules` | 素材 ID | 审核状态、缺失字段、风险；检查已读取内容 |
| `query_slots` | 素材 ID | 同日时段及空闲状态，包含已确认本地草稿的占用 |
| `save_draft` | 素材 ID、建议时间 | 写入结果、草稿、是否重复；再次核对审核与时段 |
| `finish` | 简短结束依据 | 请求结束；程序从工具记录汇总最终结果 |

每个工具带有简短 `reason`，用于解释本次动作依据，不要求或保存模型内部思维过程。

## 硬性要求如何保留

业务请求由调用方传入，工具参数不能新增 `approved_slot`。草稿分别保存 `requested_slot`、`suggested_slot`、`effective_slot`。硬性要求发生变化且没有对应批准时，第三个字段为空，`pending_confirmation` 为真。

这样即使模型选择了备选时段，也不能把建议写成已确认安排。最终输出由程序生成，模型在 `finish.reason` 中声称成功或发布，不会覆盖工具状态。原始结束依据仍留在 Trace 中，便于审查。

## 去重和文件保存

草稿 ID 由素材 ID、原始时间要求、批准时间及素材内容计算。建议时间不参与去重：同一请求再次运行时，即使模型另选了一个备选时段，也返回首次保存的草稿及其实际建议时间。素材或原始要求改变视为新请求。

存储使用排他锁和临时文件后重命名；锁冲突返回 `STORE_BUSY`。保存时再次检查已有排期和已确认草稿。待确认草稿只是建议，不占用时段。此实现满足本地演示的重复执行与写入互斥需求，不宣称具备数据库事务能力。

## 文件逐项说明

| 文件 | 实际承担的工作 |
| --- | --- |
| `src/cli.js` | 解析命令行、加载夹具、选择模型、输出 JSON 和退出码 |
| `src/agent.js` | 执行模型循环、控制轮次、记录 Trace、汇总状态 |
| `src/providers.js` | 真实 HTTP 模型适配与明确隔离的离线策略 |
| `src/prompt.js` | 说明工具使用、补查、风险、冲突和人工确认要求 |
| `src/schema.js` | 工具 Schema、动作参数校验、请求格式校验 |
| `src/business-tools.js` | 素材读取、规则检查、时段观察、保存前限制和结果投影 |
| `src/store.js` | 草稿持久化、去重、锁和保存时冲突检查 |
| `data/world.json` | 合成素材、补充资料、审核规则、时段和占用 |
| `scripts/cases.js` | 评估用例定义、预期状态和故障注入 |
| `scripts/evaluate.js` | 实际执行用例，写入输入、输出、Trace 和草稿快照 |
| `scripts/run-tests.js` | 运行测试并保留 TAP 原始报告与摘要 |
| `scripts/verify-evidence.js` | 独立核对运行输出、Trace 与草稿是否一致 |
| `tests/agent.test.js` | 验收场景、确认边界、保存约束、状态和上限测试 |
| `tests/provider.test.js` | 模型协议、观察回传和上游错误处理测试 |

## 技术取舍

选择 Node.js 原生实现，省去依赖安装，把有限时间留给业务行为和证据。当前循环规模较小，不需要图编排框架。后续若引入跨天审批或长期任务恢复，再考虑数据库和状态机。

模型协议依据 [Kimi 官方工具调用文档](https://platform.kimi.com/docs/api/tool-use)接入。服务端可返回多个工具调用，但本项目每轮只接受一个，便于控制次数和核对因果顺序；不符合约定时返回未完成。
