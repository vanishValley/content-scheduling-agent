# 需求与验收标准

## 用户和要解决的问题

内容运营准备发布素材时，需要先确认资料是否完整、素材是否符合规则、要求的时段是否可用。若其中一步失败，运营人员需要知道卡在哪里，以及下一步由谁处理。

本项目把这些工作收敛到一个 CLI 请求中。结果既能供运营人员阅读，也能让测试逐字段核对。素材、规则和排期全部为合成数据。

## 输入约定

一次请求处理 1 至 10 个素材。同一请求中 ID 不可重复。必填字段为 `material_ids`、`desired_slot` 和 `hard_time`；`approved_slot` 可选，表示用户已明确批准的备选时间。缺少业务字段时直接返回 `needs_input`，不消耗模型调用。

时间使用北京时间 `+08:00`，当前演示按同日离散时段查询。样例日期用于可重复测试，不做“是否晚于当前时间”的校验。

素材元数据包含标题、说明、平台和版权状态。`owned`、`licensed` 可通过版权检查；`unknown` 或无法识别的值须阻断。规则还检查必填项与禁用声明。补充资料必须实际存在于 `supplements`，Agent 不得猜测缺失字段。

## 输出约定

| 字段 | 运营人员可以据此判断什么 |
| --- | --- |
| `audit_status` | 尚未检查、通过、信息缺失或风险阻断 |
| `risks` / `missing_fields` | 哪些问题需要处理 |
| `suggested_slot` | 模型实际选择并尝试保存的建议时段 |
| `pending_confirmation` | 是否仍需补资料、处理风险或批准改期 |
| `save_status` / `draft_id` | 未尝试、已保存、复用已有草稿或失败 |
| `status` | 本项素材的最终任务状态 |
| `trace` | 动作、工具参数、返回结果和简要依据 |

`suggested_slot` 在保存失败时仍可保留建议，但不得被理解为保存成功。是否成功以 `save_status` 和草稿文件为准。

批量请求保留每项素材的状态。总体状态按 `incomplete`、`blocked`、`needs_input`、`needs_confirmation`、`completed` 的顺序汇总，不能用总体失败覆盖已经保存的素材。

## 六项必验场景

| 场景 | 合成输入 | 成功标准 |
| --- | --- | --- |
| 正常排期 | M01，要求 19:00 | 审核通过，保存一份 19:00 草稿，输出未发布 |
| 素材信息缺失 | M02 缺少版权字段 | 返回缺少 `rights`，不保存；M04 有补充资料时可补查后继续 |
| 规则风险 | M03 含禁用声明，版权未知 | 返回两条风险并阻断，不保存 |
| 时段冲突 | M01，硬性要求 18:00，该槽位占用 | 建议 19:00，保留原要求，草稿待确认，`effective_slot` 为空 |
| 重复提交 | 相同请求在同一目录执行两次 | 第二次返回 `duplicate`，草稿总数仍为 1 |
| 保存失败 | 保存工具持续失败 | `save_status: failed`、总体 `incomplete`，没有虚假草稿 ID |

另外验证更换占用时段、用户批准改期、工具读取失败、没有可用时段、多素材部分完成和执行上限。完整记录见 `examples/`。

## 范围与边界

代码没有真实发布接口。已确认草稿仅在本地演示中占用时间槽，待确认建议不占槽。保存时会再次核对冲突，查询结果不能代替最终检查。

本次不做 UI、线上部署、账号权限、真实素材审核、多 Agent 和生产级 Runtime。优先把模型动作、状态变化、人工确认及保存结果核对清楚。
