# 第 3 题：企业知识问答 Agent 方案

本题是备选设计，未提交问答代码或实际模型结果。下述制度是合成测试资料。

## 用户和结果

员工输入制度或产品问题，可附对话历史。Agent 给出有原文依据的回答、文档 ID 与原文片段、资料缺口和任务状态。资料不够时应追问，制度冲突时应把冲突说清楚。

每份文档包含 `document_id`、`version_date`、`scope`、正文和可选优先级。版本日期是线索，不能在没有适用范围或替代关系时，直接认定“最新文档优先”。

## 检索与读取为什么分开

`search_documents` 返回候选文档 ID、版本和检索摘要；`read_excerpt` 返回文档中的实际片段及段落位置。模型先依据候选决定读哪些原文，再形成回答。检索摘要不直接充当引用。

初次检索无结果时，模型可以改写查询一次或请求补充。上下文追问时，需要结合历史还原指代，例如“那异地出差呢”应延续报销话题，再检索适用范围。无法可靠还原时先追问。

回答可采用结构化输出：`answer`、`citations`、`gaps`、`status`。引用项包含文档 ID、版本、片段 ID 和逐字原文。程序可校验原文是否存在于本轮读取结果中；是否足以支持答案仍需用例核对。

## 冲突路径如何展示

测试设计：D01 写报销期限 30 天，D02 写 15 天，均未说明适用范围。模型应读取两份原文，发现不一致后继续查适用范围或替代关系。仍无资料时列出两条规则和引用，请用户确认制度适用条件。

对照用例只提供 D01，并确认没有其他相关资料，此时可回答 30 天。再把 D01 改成 20 天重跑，答案和引文应随原文改变，防止模型背诵固定答案。

| 文件 | 职责 |
| --- | --- |
| `src/agent.js` | 检索、读取、补查、追问和结束的模型循环 |

| `src/tools/search.js` | 按词项、同义词和历史问题检索，返回候选 |
| `src/tools/read.js` | 按文档与片段 ID 返回原文 |

| `data/synonyms.json` | 首版使用的小型同义词表 |

## 验收设计

| 场景 | 应核对的结果 |
| --- | --- |
| 明确答案 | 回答与原文一致，引用可定位 |
| 文档冲突 | 至少读取冲突双方，说明缺失的适用条件，不擅选期限 |
| 资料外问题 | 返回资料缺口，不能凭通用知识编造公司规定 |
| 改写后的相似问题 | 查询方式可变，证据和结论应一致 |
| 上下文追问 | 正确还原话题；无法判断时追问 |
| 工具失败 | 显示失败，不把未读取的摘要包装成原文引用 |

至少保留一条“无结果后改写检索”或“冲突后补查”的真实模型路径。仅有检索一次后固定拼接答案，不能证明动态决策。

## 主要取舍

资料只有十几份时，可先用可解释的词项检索与同义词表，无须先部署向量数据库。检索的改进应通过改写问题的召回结果验证。首版将精力放在引用和冲突处理，避免检索架构复杂却无法证明答案依据。
