# 第 1 题：素材审核与发布排期

## 做成什么

运营人员给出素材与发布时间要求，Agent 输出审核结果、风险原因、建议时段、待确认事项和草稿保存状态。当前实现位于仓库根目录，运行方式为 CLI。

关键场景是“用户要求 18:00，但只能找到 19:00”。结果必须同时表达：原要求仍为 18:00，19:00 是建议，改期未确认，建议草稿是否实际保存。

## 实现思路

模型先读取素材，再依据规则结果决定继续还是补查。审核通过后查询可用时段，由模型挑选原时段或备选，再调用保存工具。工具统一限制：资料不完整不能保存，未通过规则不能保存，未查到空闲不能保存，硬性改期不能自行确认。

正常路径是五轮动作：读取、审核、查询、保存、结束。补查路径增加读取，必要时重新审核；真实模型这次选择连续读取两次，再审核和保存。工具失败后把错误交还模型，由模型决定补救或结束；最终状态保留实际失败。

## 文件为什么这样划分

业务约束放在 `src/business-tools.js`，循环放在 `src/agent.js`，服务接入放在 `src/providers.js`。这样修改模型服务时，不必改去重和确认规则；替换合成素材时，也不必改循环。

`src/store.js` 单独负责文件保存，便于检查重复、互斥和失败。`data/world.json` 保存资料和规则，评审可以直接改变占用时间或素材说明。`scripts/cases.js` 固定输入与预期，`examples/` 保存执行后的输出，而不在代码中预写 Trace。

完整文件表见[实现说明](../02-solution.md)。需求、评估、AI 使用和复盘分别位于 `docs/01` 至 `docs/05`。

## 验收怎么看

先运行 `npm test` 与 `npm run evaluate`，再检查以下三处：冲突用例的 `effective_slot` 应为空；重复用例第二次应为 `duplicate` 且只有一份草稿；保存失败时草稿列表应为空。

真实模型运行记录在 `examples/live/`，可比较正常、冲突、补查、阻断几条路径。`examples/regressions/` 保留首次缺资料误判及改进依据，详见[评估文档](../03-evaluation.md)。

## 可以解释的取舍

本地文件减少依赖，方便评审运行。代价是崩溃恢复和草稿版本管理较弱。规则采用确定检查，便于核对误报与漏报；它不具备视觉审核或法律判断能力。暂不加入真实发布工具，避免把题目的草稿任务扩大成发布系统。
