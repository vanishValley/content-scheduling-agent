# 实现复盘

## 最需要仔细处理的地方

排期建议、用户确认和保存成功是三个独立事实。18:00 已占用时，19:00 可以是合理建议，但不能因此改掉用户的硬性要求。写入磁盘成功，也不等于用户已经同意，更不等于素材已发布。

实现上分别保留原要求、建议时间和有效时间，再由保存工具判断是否待确认。测试直接检查这些字段和草稿文件，比只看一段“排期成功”的说明更容易发现问题。

重复提交也需要考虑模型可能改变选择。以建议时间参与去重时，模型第二次换一个时段就会生成新草稿。复核中据此增加反例，改为按原始请求去重；重复调用返回原草稿，输出也使用原草稿中的时间。

## 实际遇到的问题

测试构造了一个保存失败、模型却声称“全部发布”的结束动作。最初代码保留了错误文案，虽然状态仍是失败，读者仍可能被误导。修改后，模型可以解释为什么结束，但不能编写最终的保存结论。

真实模型联调没有完成。第一次连接失败，后续外部凭据调用未获自动审批。失败记录已保留，真实能力的结论也停在未验证，没有用离线策略替代证据。

## 从实现中得到的判断

模型适合依据观察选择下一步，例如发现有补充资料后再读一次，或在冲突后改选备选时间。参数范围、保存权限、去重和状态计算需要明确代码约束。两部分分开后，可以单独测试模型协议，也能用反例检查工具是否允许越界。

另外，运行记录本身也需要核对。输出写着已保存时，应能找到对应草稿；相同请求再次保存时，应返回原 ID；Trace 的每一步应来自本次执行。为此增加了证据核对脚本，而没有只提交截图。

## 下一步按什么顺序做

第一步是补真实模型的成功与失败路径，记录不同观察是否确实改变动作。第二步是让候选人自己改一次素材或排期，再把实际修改和结果写进 AI 使用文档。第三步才考虑将本地草稿搬到数据库，补上确认事件和旧建议归档。

更复杂的 UI、多 Agent 和线上部署暂时不影响本题核心验收，当前没有加入。个人学习收获及实际用时需要候选人结合自己的操作补写，本节只记录本次实现中已有证据的发现。
